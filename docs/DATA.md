# Data import boundary

P03 imports only the reference `questions` table. Authentication, games, teams, answers, displays and runtime logs are never copied.

## Source and mapping

- Reference source: `~/dev/trivia-party/pb_data/data.db` (explicit `--source` only).
- The source is opened through SQLite URI `mode=ro`, then copied with SQLite's online backup API to an ignored snapshot before rows are read.
- Source rows are ordered by the PocketBase `id`; that value becomes the target `source_id`. The target integer `id` is generated by SQLite.
- `external_id` is not used as the identity and may repeat. Empty strings and nullable source values are preserved. Text is not trimmed, parsed or defaulted. `level` must already be numeric and is stored as the target REAL value; malformed values fail the import.
- The target mapping is `source_id`, `external_id`, `category`, `subcategory`, `difficulty`, `question`, `answer_a`, `answer_b`, `answer_c`, `answer_d`, `level`, `metadata`, and `imported_at`. `ingested_at` remains server/database-owned.

The current reference schema has 591,183 rows at the recorded baseline, but that count is observation only; P03.T3 records the fresh snapshot count rather than assuming it.

## Destination safety

`pnpm import:questions -- --source <db> --depot <owned-depot>` requires a stopped, marked local depot with:

- a `.owner` marker for this repository (`trail-party-dev-v1` or `trail-party-import-v1`);
- `data/main.db` containing the P02 `questions` table; and
- no cooperating TrailBase `<depot>.lock`.

The importer creates a short-lived `<depot>.import.lock`, writes only under the ignored depot `import/` directory, uses parameterized inserts, and commits all question rows in one transaction. A missing source is checked before any destination state is created. Unmarked, foreign, symlinked or locked destinations are refused. Source and destination database paths must differ.

Each run creates `import/questions.snapshot.sqlite`. A successful non-dry run also writes the ignored `import/questions.manifest.json`; neither belongs in Git. Dry-run validates and reports the source/destination/count/digest without inserting application rows.

## Repeat and conflict policy

A row with the same `source_id` and identical mapped fields is skipped on a rerun. A changed row with an existing `source_id` is a source conflict: the transaction rolls back and the existing target row is retained. Invalid rows fail before the target transaction, rather than being silently coerced or partially accepted.

The manifest digest is SHA-256 over newline-delimited canonical JSON mapped rows ordered by `source_id`; nullable values remain JSON `null`, Unicode is emitted without ASCII escaping, and numeric `level` is normalized to the target REAL representation. It excludes target `id`, `ingested_at`, and private/runtime data. Public evidence contains only counts, digests, commands and sanitized paths; the corpus, snapshots and raw manifests remain local/ignored.

The importer uses the host Python stdlib SQLite engine only for read-only source backup and validation. It does not call TrailBase-only SQL functions such as `jsonschema_matches`; the stopped destination is opened with SQLite foreign keys enabled so the pinned TrailBase schema remains the final constraint authority. The verifier registers small local compatibility implementations of the pinned schema predicates before running SQLite integrity checks; it does not depend on unavailable extension functions or change the depot schema. Type normalization is limited to the target `REAL` representation for `level`; other values are preserved or rejected, never silently defaulted.

P03.T1 proves the synthetic source-safe path. Interruption/resume, full-corpus verification and real API retrieval are owned by P03.T2/T3 and are not claimed here.
