# P02 API contract — design plus current implementation boundary

P02 is in progress. This is the closed target surface plus the explicitly implemented T1/T2/T3 subset; it is not a phase-acceptance claim. T1 schema/projections are implemented, T2 includes native local-mail auth, origin-scoped browser session handling, validated return-to intent, and the authenticated `POST /api/trail-party/profile` command, and T3 now has the real actor/forgery selector and safe event-projection tables. The remaining handler inventory, avatar/device commands and gameplay surfaces are still design obligations. Schema is in [ARCHITECTURE](ARCHITECTURE.md#p02-design-contract--data-model-not-implementation); permissions and executable case names are in [ACCESS](ACCESS.md). Only synthetic fixture games/questions/memberships are permitted in P02. Host setup, join/team commands, question allocation, gameplay transitions, answers/grading/scoring, timers and full display rendering remain P05–P10.

## Current T2 implementation boundary

- `backend/functions/profile.ts` derives identity only from the verified native `HttpRequest.user()`, accepts the closed `display_name`/`operation_id`/`issued_at` command, writes the profile and audit row transactionally; the migration trigger maintains the safe event projection in that transaction, and returns only the `profiles_public` safe fields. The auth backend selector deploys this component; `pnpm dev` builds and installs it into the owned development depot.
- `src/routes/auth/+page.svelte` implements native registration/verification-pending/sign-in/MFA/reset-request/profile-create/restore/logout states. Native v0.33.14 sends the initial pending verification message but cannot resend to an unverified address; the UI states that limitation rather than claiming a resend succeeded. Reset-link consumption remains native and the pinned replay residual remains documented.
- `src/lib/backend/session.ts` persists only structurally validated native tokens in origin-scoped `sessionStorage`, validates native status before protected profile reads, and clears local state even when logout cannot be confirmed. `src/lib/return-to-origin.ts` validates and one-shots only approved same-origin relative paths.
- The current browser probe proves the real registration/verification/login/profile request against a fresh owned auth stack and Mailpit, but it is not the P04 authenticated multi-user E2E gate. Google OAuth, avatars, gameplay, P02.T3 authorization and native secure storage remain unimplemented or externally gated.

## Pinned transport, not invented SDK methods

Use TrailBase **0.33.14**, source **3f965de7ea516c43a54ca70a495e97f0c6d991ab**, SQLite **3.53.2**, official `trailbase` **0.14.1** with the existing pinned SSE patch, and `trailbase-wasm` **0.6.0**. [STACK](STACK.md#p01t2-measured-contracts), `tests/backend/capabilities.test.ts`, and `tests/backend/fixture/component.ts` distinguish real probes from design. Local pinned sources/help are under `.artifacts/p01-t2/upstream/` and `.artifacts/p01-t2/schema-help.txt`; ignored artifacts are evidence, not required production dependencies.

- [Pinned client.ts](https://github.com/trailbaseio/trailbase/blob/3f965de7ea516c43a54ca70a495e97f0c6d991ab/crates/assets/js/client/src/client.ts): `initClient(base, {tokens,onAuthChange})`, `user()`, `tokens()`, `headers()`, `fetch(path, init)`, auth calls below. User is not the application profile. Constructor session checking is asynchronous: `user()` being present immediately after construction is **not** session validation.
- [Pinned record_api.ts](https://github.com/trailbaseio/trailbase/blob/3f965de7ea516c43a54ca70a495e97f0c6d991ab/crates/assets/js/client/src/record_api.ts): `client.records(name).read(id)`; `.list({filters,order,pagination,count,expand})` returns `{records,cursor?,total_count?}`; `.create(record)` returns the ID, `.update(id,partial)`/`.delete(id)` return void. No PocketBase-shaped response assumption. `filePath(apiName,recordId,columnName)` exists; it is a URL builder, not permission or upload proof.
- Record wire base: `/api/records/v1/<api>`; GET list, GET `/<id>`, POST create, PATCH `/<id>`, DELETE `/<id>`. P02 denies all direct mutations, including bulk/transaction paths. Schemas are generated locally with `trail --depot <owned> schema <api> --mode insert|select|update`; remote schema access, if enabled, is subject to the same safe-column policy and is not an authorization bypass.
- `.subscribe(id)` and `.subscribeAll({filters,onLoss})` return ReadableStreams. `reader.cancel()` then `releaseLock()` owns teardown. Filters optimize delivery, **never authorize**. The SDK patch repairs framing, not reconnect/revocation. No unrestricted expand; every API has an empty expand allowlist in P02.
- `FetchError` is checked by `instanceof FetchError` and `.status`; it implements but does not extend Error. Do not swallow exceptions as empty records. Native Record status details not measured in T2 (unique/FK/excluded-column errors) are pinned by the first red tests, not promised from memory.
- Small proposed `/api/trail-party/...` routes below are **new TrailBase authenticated WASM handler contracts**, not SDK methods or existing routes. Call with `client.fetch`. Trusted `HttpRequest.user()` and synchronous parameterized `Transaction.query/execute/commit/rollback` were measured by T2. No await inside a transaction. Bind UUID user parameters with the proven `base64_url_safe(?)` SQL conversion; reject malformed IDs before SQL. Exact binary file/crypto integration must be proven in T2 before enabling those handlers.

## Common request and failure contract

All custom mutation inputs are closed schemas, with no extra keys. JSON bodies <=8 KiB except avatar bytes (5 MiB plus bounded multipart framing). IDs are correctly decoded UUIDs; versions safe nonnegative integers. Caller-supplied identity, host, device, role, translated answer, grade, key, score or ownership is never authority. A game/record ID selects a target that must then be authorized against live rows. No generic arbitrary-field mutation endpoint.

Every custom mutation supplies `operation_id` (canonical UUIDv7 text), `issued_at` (Unix seconds matching the UUID's embedded timestamp rounded down to seconds; <=24 hours old, <=60 seconds future) and, for existing targets, `expected_version` (or the explicitly named game/claim version below). Server validates timestamp binding, so an expired ID cannot be replayed with a new issued_at after audit retention. Record request HMAC/action/entity and successful resulting version in append-only audit in the mutation transaction. Same actor+operation+identical input is idempotent **after current authorization is rechecked**; changed input/action/entity returns 409 without mutation. For a known replay retain the original result version and return a fresh authorized snapshot separately; never replay old secrets or claims. Expired operations return 409, not a new mutation; same-operation idempotent retries are within the 24-hour validity window. Rate-limited retries cannot avoid attempt limits. Sensitive code/avatar responses are not stored in audit. See ARCHITECTURE for retention.

Custom responses: 200 safe result; 400 malformed/unknown field/invalid return target; 401 no valid session; 403 forbidden actor category; 404 missing or inaccessible resource (no foreign IDs/current state in error); 409 stale version, idempotency mismatch, constraint/race conflict; 413 oversized body; 415 unsupported avatar; 429 bounded rate limit with Retry-After; 503 unavailable backend/mail/file service, visibly retryable. Successful create/enroll may use 201 as pinned by its first test. Conflicts include current version/safe projection **only if still authorized**; failed code claim uses one generic unavailable-code error. Native auth/Record responses retain actual pinned statuses and are mapped to these UI states, not rewritten to fake success. Mutation/audit failure rolls back everything except separately committed denied-attempt counters/audit. No SQL errors, hashes, codes or private values in responses/logs.

## Authentication and session surface

Auth uses `/api/auth/v1` through the SDK/native endpoints, never an app-owned password table. All auth operations have no Record expand/SSE. Native auth has no application `expected_version`/operation_id. Verification tokens are one-use in the pinned engine; the pinned v0.33.14 password-reset source and red probe show reset tokens are stateless/replayable (a second update returned HTTP 200). The owner approved a narrow re-scope: P02.C2 must characterize the replay and record its explicit upstream residual risk, without claiming reset tokens are single-use or secure against a holder who replays one. Do not put passwords, JWTs, refresh tokens, mail bodies or links in application audit/Git. Auth delivery attempts need bounded native/edge rate limits and sanitized private logs, not credential-bearing event rows.

| Operation / method and input | Actor / output / failure / proof boundary |
|---|---|
| Register: `client.register({email,password,passwordRepeat,options:{redirectUri}})`; POST `/api/auth/v1/register` | Anonymous prospective user; SDK returns void, **no session**. Backend enforces email verification; show verification-pending and resend/retry, not immediate login. Username-only auth policy is not relaxed for displays. Native wire fields include email/username/password/password_repeat/redirect_uri. Fixed allowlisted callback only; keep join intent locally. Failure to send mail is visible/recoverable. |
| Verification/resend: native email verification request and consume-link endpoints, through `client.fetch` or navigation | Unauthenticated pending account; bounded email input and one-time link/token; pending -> verified -> ordinary login, no app data access before verification. Resend does not create a second account. **First red test `auth-local-mail`: confirm exact HTTP methods, paths, body/redirect and expiry/reuse statuses from pinned [verify_email.rs](https://github.com/trailbaseio/trailbase/blob/3f965de7ea516c43a54ca70a495e97f0c6d991ab/crates/core/src/auth/api/verify_email.rs).** No `requestVerification`/`verifyEmail` SDK method is assumed. |
| Login: `client.login(email,password)`; POST `/api/auth/v1/login` | Verified user; SDK stores tokens and returns undefined or a multi-factor challenge, not a profile. Never treat a challenge as authenticated app success. Invalid/unverified login remains pending/error. F02 does not add MFA management in P02, but must not bypass a returned challenge. |
| Refresh: `client.refreshAuthToken({force:true})`; POST `/api/auth/v1/refresh` | Existing real session, native refresh_token body; boolean return is not sufficient—check resulting validated identity. Real T2 proves valid refresh/identity. Definitive refresh 401 clears token state; network/5xx is retryable and must not delete identity or silently enroll another device. Old access-JWT immediate revocation is **not** proven. |
| Status/reload: native GET `/api/auth/v1/status`, SDK token initialization/onAuthChange | Validate restored session before protected record/command/SSE activity; no role inferred from URL or stored profile. First red confirms authoritative verification/anonymous/session-revocation behavior. |
| Logout: native POST `/api/auth/v1/logout` with refresh_token (or native GET cookie mode); `client.logout()` clears local state | Existing session; cancel streams/in-flight work and clear role-specific caches/storage even on offline failure. **Pinned SDK logout catches errors and returns true anyway.** A true result alone is not server-revocation evidence: use the native response where needed to surface failure and prove refresh rejection in tests. Do not claim immediate revocation of existing access JWTs. |
| Password reset request/consume: native reset endpoints via `client.fetch`/link navigation | Anonymous or existing account; bounded email request yields enumeration-safe acknowledgement and an expiring native flow. **Measured pinned v0.33.14 [reset_password.rs](https://github.com/trailbaseio/trailbase/blob/3f965de7ea516c43a54ca70a495e97f0c6d991ab) accepts the same token again (HTTP 200) and can change the password again; owner-approved option A characterizes this as an explicit upstream residual rather than claiming one-use.** No invented SDK reset method. |
| Google OAuth start/callback: native TrailBase OAuth flow, static SPA return page | Local controlled-provider check must prove callback/state/PKCE/nonce/return binding using the pinned configuration; no invented `authWithOAuth2` SDK method. Exact native flow is a first-red P02 check. Real Google credentials/callback registration are an **external owner gate** in P12; show unavailable honestly when absent. P02 does not require or claim real Google success. |
| Anonymous display identity: `client.loginAnonymously()`; POST `/api/auth/v1/login_anonymous` | New display context only, returns void with native anonymous tokens. Do not allow it to create profiles or impersonate verified people. Refresh/status as above. No `/api/_admin/user`, CLI promotion, fake verified email/password, token minting or browser administrator capability. |

**Local mail gate:** The current T2 backend selector runs actual register -> pending -> native verification link -> login -> reset -> login -> refresh -> logout -> rejected refresh reuse against a fresh owned TrailBase/local SMTP sink. It also records that `verify_email/trigger` returns the privacy-preserving success response but delivers no message for the pending `unverified_email`; the UI does not expose a false resend action. The verified-fixture resend path is tested separately. P02.C2 remains a parent acceptance decision, not an automatic consequence of this selector: final review, evidence synchronization and the real browser boundary remain explicit. Reused-link, reset-replay, identity, profile boundary and logout assertions are present; expired-link, mismatched-password, delivery-failure and rate-limit cases remain proof obligations and are not claimed by the current selector. Under owner-approved option A, the reset check characterizes the real second-password replay and records the non-zero upstream residual; it must not call replay single-use or secure. Fetch messages only from the isolated test inbox; never send production mail or use CLI verify for this scenario. P04 drives the same flows in real browsers. Production SMTP and Google secrets remain outside Git.

### Validated same-origin return-to and join intent

Treat returnTo, OAuth state targets and role hints as untrusted. Persist only a validated relative route in **sessionStorage**, scoped to SPA origin, with 30-minute expiry and consume-on-success; never embed it verbatim into auth redirect_uri. Use fixed configured `/auth` callback URL(s) accepted by backend, never derive a trusted origin from arbitrary Host/forwarded headers.

Allow only `/host`, `/lobby`, `/join?code=<six uppercase ASCII letters/digits>`, and correctly encoded `/game/<id>` or `/controller/<id>`. Role is only host/player navigation preference, never permission. Reject absolute URLs even to same origin, `//`, backslashes, control characters, credentials, fragments, malformed/double-encoded separators, unknown query keys and nested returnTo. Parse once against the configured origin, require exact origin/path allowlist and reserialize only approved parameters; validate again immediately before navigation. Default invalid/expired intent to `/lobby` (or `/host` from a valid role hint), without following the invalid URL. Unit/backend `return-to-origin` tests include encoded protocol-relative URLs and misleading `https://allowed@evil` cases. Game access is independently checked server-side after navigation. Future join execution remains P06; P02 tests intent preservation, not gameplay.

Browser user tokens use origin-scoped sessionStorage (no cross-actor storage state); display tokens and the current pairing code use origin-scoped durable storage for restart, separated by backend origin and anonymous user ID. Both are accessible to same-origin JS: CSP/XSS prevention is mandatory, not encryption theatre. Native durable token storage requires the platform secure-store decision/proof in P09/P11; never claim plain WebView storage is a native keystore. No credentials in URLs or telemetry. Logout clears storage, subscriptions and snapshots across same-identity tabs; a queued old response cannot repopulate a new session.

## Exposed P02 Record projections

GET/read/list only. All APIs have `acl_world` deny (except readiness), authenticated live row-rule checks, empty expand allowlist, hard list limit 100, and explicit safe columns. Client filter omission cannot broaden authorization. Every POST/PATCH/DELETE/bulk/transaction mutation is denied, including direct calls bypassing the UI. Version is output-only; mutation retries belong to commands, not Record IDs.

| API -> source / exact safe select | Actors / SSE / conflict policy |
|---|---|
| Per-start readiness -> bootstrap_ready: id, schema_version | All actors may GET the constant row; no mutation, expand or SSE. Existing P01 surface unchanged. |
| `profiles_public` -> profiles: id, display_name, avatar_mime, avatar_revision, version, updated_at | Self, current shared-game members, game host and currently paired display viewing that game's roster. No email, auth flags, file metadata/path or size. Authorized filtered SSE permitted only after excluded-column and revocation proof. Avatar URL is constructed as the protected app handler URL, not stored/exposed objectstore_path. |
| `games_public` -> games: id, title, location, starts_at, duration_minutes, lifecycle, roster_locked_at, roster_version, version, updated_at | Game host, current member (including locked rejoin member), paired display. Not a public games directory or join-code lookup. Game-scoped SSE after proof; no key/grade or host-sensitive settings. |
| `games_host` -> games: games_public columns plus host_id, join_code, timers, auto_reveal | That game's verified host only; own-game filtered SSE. No device audience. host_id is descriptive output, immutable authority comes from database. |
| `game_teams` -> game_teams: id, game_id, name, version, updated_at | Game host/member/display; non-deleted teams in authorized game. Game-scoped SSE. |
| `game_players` -> game_players: id, game_id, user_id, team_id, left_at, version, updated_at | Game host/member/display; no private auth joins. Game-scoped SSE. Teammates/opponents see roster, not each other's unrevealed answers. |
| `game_state_public` -> game_state_public: all columns listed in ARCHITECTURE | Game host/member/display; only current question and shuffled choices, no bank/source IDs or unrevealed secrets. Game-scoped SSE. No gameplay population/advance handler in P02. |
| `displays_public` -> displays: id, game_id, host_id, claim_version, settings, version, updated_at | Its own anonymous device, or current verified claiming host (own game). No world available-device listing; host must claim by code command. Row/game-filtered SSE after proof. No device_user_id/hash/code/expiry/attempt/last-seen/revocation disclosure. |
| `online` -> online: id, game_id, last_seen_at, visibility, version | Game host/member/display scoped reads/SSE. Presence is not membership or scoring authority. No direct heartbeat write in P02. |

Use the pinned RecordApiConfig `excluded_columns` rather than only `_` hidden fields when an API reads a source table directly. TrailBase v0.33.14 still serializes excluded source columns in SSE events, so `backend/migrations/main/U1789084930__p02_t3_safe_event_projections.sql` maintains allowlisted physical mirrors for APIs that need subscriptions; the mirror tables are not additional client APIs. `authority-forgery` proves exact safe output, scoped reads, direct-mutation denial, expand denial, foreign SSE denial and the mirror-table column boundary; `auth-local-mail` now proves a trusted profile-create insert event contains only the safe fields. Update/delete delivery and already-open-stream revocation remain explicit C3 proof obligations; no private-table fallback is permitted.

**No direct client collection, expand or SSE exposure in P02 for private answer/key/grade/score/assignment data:** questions, rounds, game_questions, assignment_private, game_answers, answer_grades_private, used_question_history, audit_events and pairing_limits have no Record config. Base profiles/games/displays are also unexposed; aliases above only. Even a synthetic revealed state does not enable secret output. Future answer/score projections require their owning P07 design/negative tests, not unused P02 endpoints.

## Minimal authenticated handler inventory

The profile create route below is implemented in the current T2 checkpoint; the remaining routes are proposed and not currently available. Custom mutations follow the common exact input/version/idempotency/error policy. No handler accepts an actor/role/owner field. No handler supports expand or SSE. Read handlers return no-store responses and enforce the same live roster/device scope as Record rules.

| Method / proposed path | Input and actor | Output / authority and conflict behavior |
|---|---|---|
| POST `/api/trail-party/profile` **(implemented T2 subset)** | Verified user; display_name, operation_id, issued_at. No id/host/avatar fields. | Derive profile ID from authenticated user. Create once + audit atomically; same-operation retry converges, another existing-profile create conflicts. Return own profiles_public projection. Anonymous/unverified callers, unknown fields, forged identity and invalid timestamp bindings are denied.
| PATCH `/api/trail-party/profile` | Verified profile owner; display_name, expected_version, operation_id, issued_at. | Validate name and CAS profile + audit; ownership/id/server-time changes rejected, 409 for stale version with own safe snapshot. No nullable name/no generic patch. |
| PUT or DELETE `/api/trail-party/profile/avatar` | Verified owner; PUT contains one file plus expected_version, operation_id, issued_at; DELETE same metadata without a file. | Validate server-observed bytes/MIME/dimensions; CAS pointer/avatar_revision/version + audit, clean temporary failures, return safe profile. No caller-provided filename path, remote URL, metadata or owner. Same bytes replay identified by keyed digest; failed replacement preserves prior file. |
| GET `/api/trail-party/avatar/<profile-id>?revision=<n>` | Self or currently authorized same-game viewer/display. No bearer tokens in URL. | Only current pointer/revision's image bytes; 404 for absent, stale or unauthorized avatar. | POST `/api/trail-party/display/enroll` | Native authenticated **anonymous** user with no display row; operation_id, issued_at. | Server-derived device_user_id; one display per identity; generate collision-checked CSPRNG six-digit code and HMAC, expiry 10 minutes; return own displays_public row plus plaintext code/expiry/code_epoch once in no-store response. No role, host or user input. Same-operation replay returns safe row only; if plaintext was lost rotate using next operation. |
| POST `/api/trail-party/display/code` | That device only; expected_version, operation_id, issued_at. Allowed only when unclaimed/unrevoked. | Rate-limited code rotation: expire prior hash, generate new code, increment epoch/version and audit. Respond once with own code/expiry, never in SSE. No claim recovery by old code. |
| POST `/api/trail-party/display/claim` | Verified game host; six-digit code, game_id, expected_game_version, operation_id, issued_at. | POST `/api/trail-party/display/reassign` | Current claiming verified host; display_id, new_game_id, expected_version, expected_claim_version, expected_game_version, operation_id, issued_at. | Both current and destination games belong to caller, destination not deleted/completed. `displays_public.read/list` is the refresh/reconcile primitive after SDK status/refresh, not another bootstrap endpoint. Before any protected action, check the anonymous identity still exists and matches device_user_id. A definitive unrecoverable refresh 401 clears local identity/code and requires `loginAnonymously()` plus new enrollment and host pairing. Never copy the previous claim; transient HTTP/network/SSE errors retain tokens/identity and retry. Old display scope must be rejected when its auth identity is gone/revoked. P02 proves backend primitives and fixture race/expiry/loss cases; P09/P10 own visible startup/completion/reconnect/native behavior and theme controls.

### Remaining pinned proof obligations (fail closed)

- `schema-two-depots`/`projection-rest-expand-sse`: exact safe alias insert/select/update schema behavior; exclusion under REST/filter/count/SSE and ongoing revocation; disabled endpoints are not a passing permission test.
- `auth-local-mail`: exact native verification/resend/reset/OAuth callback details, local mail delivery/error visibility, verified-vs-anonymous checks against the pinned built-in schema, logout/status/session behavior. Native endpoints are not reimplemented as password handlers.
- `avatar-boundary`: native single-file metadata/size/MIME controls, actual byte validation, authenticated read and temporary-file cleanup integration. SDK `avatarUrl()` points at native auth avatar but **is not used**: it does not prove our roster-only policy. Do not expose `/api/auth/v1/avatar` or generic Record file paths as an app avatar workaround; prove no bypass on aliases. If native storage cannot supply the required checks to the authenticated boundary, stop and obtain a bounded design correction rather than add a custom file subsystem silently.
- `device-claim-lifecycle`: HMAC/CSPRNG availability and secret loading in pinned WASM, anonymous identity classification, attempt persistence/expiry, atomic audit/CAS, no transfer on refresh loss, subscription revocation. No SDK peer-IP helper is assumed. Actor/global DB buckets are the P02 brute-force boundary; public anonymous-account creation also needs edge/global protection before release.

No SvelteKit server routes/actions, PocketBase compatibility layer, generic ORM/repository, event bus, admin/browser bootstrap or gameplay transitions in P02. No production credentials, CI publication, data import or native packaging is authorized by this contract.
